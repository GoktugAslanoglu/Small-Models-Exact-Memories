Identifier layout follow-up: prospective protocol, 21 September 2026

This is a new study prompted by the completed audit. It cannot retroactively explain the original study as a prospectively tested mechanism. The original 13,176 responses and primary analyses remain immutable. No follow-up response has been generated when this protocol is sealed.

The question is whether recoverability changes under a source-preserving layout intervention at fixed measured C=2, and whether a deliberately readable optical regime can be demonstrated. No universal capacity, precise entropy interaction, or model-size scaling claim is planned.

**Fixed design.** Development uses 12 fresh cases, three layouts, Qwen2B only: 36 calls. The evaluation uses 48 fresh cases, four conditions, three readers: 576 calls. Total identifier ceiling: 612 attempted generations. Failures do not create permission for additional calls. There is one development selection round and no case replacement. Code, cases, seed rules and assets are hashed before development inference; selected-layout and all-reader input hashes are sealed before evaluation inference.

Source construction uses the validated identifier family, an 8,192±32-token Qwen reference-tokenizer source length, four distractors, target source-token positions 0.1/0.5/0.9±0.02, lengths 8/24, decimal/lowercase-alphanumeric alphabets, and repeated-four-character-motif/independent-character structures. The new development seed is 2026092102; evaluation seed 2026092103; order seed 2026092104; statistics seed 2026092105; greedy inference seed remains 2026090506. Seeds use separate deterministic key/payload streams. The 12 development cells satisfy even parity of the four factor-level indices, balancing each binary factor 6/6 and positions 4/4/4. Evaluation uses all 24 factor combinations with two replicates, giving 48 cases. Development and evaluation retain their distinct frozen question/filler templates. Candidates are preserved before validation; a failure stops generation rather than resampling.

All conditions retain the identical source string, query, target and record order. Renderers receive the memory string, never the answer, target key, or target offset. Newline handling is the intended geometric intervention: the efficient layouts map each newline one-for-one to a horizontal space and record exact source spans. Original source bytes remain intact in the artifact; the appearance of whitespace is not claimed to be identical. No non-whitespace character is changed, reordered, summarized, omitted or highlighted.

**Development layouts.** All use the pinned DejaVuSansMono font at base size 12, four square pages, margin 24 and line spacing 2. L1 uses full-width character wrapping; L2 uses two columns with whitespace-aware wrapping and a 24-pixel gutter, reading down the first column then the second; L3 uses full-width whitespace-aware wrapping. Each uses the smallest feasible square on the 224..4088 side-length lattice in steps of 28. The original baseline preserves hard line breaks and uses the original renderer's minimum feasible side on the 1372..16380 lattice. There are no headings, crops, target-aware pagination or layout changes after development.

For each reader/case, C is native source-text tokens divided by measured vision tokens, not a compute ratio. A deterministic native-processor shape search uses original 28-pixel-lattice sides within 140 pixels of sqrt(source_tokens/8)×patch_size×merge_size. It selects the smallest relative C=2 error, breaking ties by smaller side. The relative error must be ≤10%. Actual full-chat image grids and placeholder counts must agree with the measured search. Original and efficient C2 conditions must have exactly equal source-token, vision-token, nonvision-token, total-input-token, grid and input-ID sequences; only pixel tensors differ. Neither a proxy tokenizer nor predicted grids can substitute for the actual processor measurement.

All three development layouts must pass source coverage, glyph support, bounding boxes, native budget and context checks before the 36 calls. If preparation is invalid, preserve the attempt and stop for review; do not run a partial development tournament. Selection is highest canonical EM over all 12 cases, then larger median minimum-page effective font-em height, then larger median maximum text bounding-box width fraction, then lexicographically smaller layout ID. A three-way zero-EM tie is still resolved by this frozen rule; there is no additional tuning round. Development outputs are excluded from evaluation estimates.

**Evaluation conditions.** Raw text; original renderer C2/four pages; selected efficient renderer C2/four pages; selected efficient renderer with a readable positive-control budget/four pages. All three readers must have all 192 requests valid before any evaluation generation.

The readable control uses the first larger lattice side whose actual processor grid yields at least 16 pixels of font-em height and at least 10 pixels for the minimum bounding-box height over the fixed ASCII lowercase-letter/digit alphabet on every page. Its vision-token budget must exceed the C2 budget. This alphabet-wide rule uses no target identity. If native resizing/context limits make it impossible, evaluation does not start; the protocol must be abandoned or explicitly amended before any evaluation outputs. Report its realized C and total input count; it is deliberately not budget matched. Geometry establishes a legibility target, not guaranteed machine readability.

**Readers and generation.** Reuse the original pinned model snapshots, native processors and chat templates, BF16, SDPA, batch size one, greedy decoding, disabled thinking, one beam, and 64 new tokens. Every saved processor tensor must match CPU preparation before generation. Exact input/output token journals, raw strings, timing, cap indicators and environment records are retained. No accuracy is printed during GPU execution. Any incomplete or inconsistent generation stops the run; no automatic retry or silent overwrite.

**Analysis.** Verify all 576 rows before scoring. Canonical identifier EM is primary and the case is the paired unit. Each reader compares efficient C2 minus original C2 using a two-sided exact McNemar/binomial test on discordant pairs, with Holm adjustment across three readers. Report the mean paired difference, gains/losses, and a 50,000-replicate paired bootstrap interval stratified within the 24 two-instance cells. CER, literal raw EM, expanded-control accuracy, raw accuracy, caps and factor breakdowns are secondary/descriptive. A floor/ceiling bootstrap interval is not proof of zero population uncertainty. Do not fit interaction thresholds from two cases per cell.

The sample is intentionally small and fixed. At the most stringent Holm step, seven gains with zero losses would be detectable by the two-sided exact test (unadjusted p=0.015625); six would not. This is an illustration of the test's resolution, not a power guarantee. Small or mixed effects can remain inconclusive. Do not add cases because a p-value is close to a threshold.

For descriptive interpretation, a reader demonstrates the prespecified useful readable regime if readable EM ≥75% (36/48); raw EM ≥87.5% (42/48) is a task-control qualification. Report counts and uncertainty regardless of threshold. Below these levels, do not quietly lower the criterion. Evidence for a positive matched-budget improvement requires a positive effect and the adjusted primary test; a non-significant contrast does not establish equivalence or absence of a layout effect. A readable-control success with little C2 recovery identifies a limitation at the tested C2 configuration, not a universal rate threshold. Readable-control failure means this interface has not demonstrated a useful readable regime under the declared criterion. Reader-specific results remain reader-specific.

**Resource and calendar gates.** One development GPU stage and three evaluation GPU stages each receive at most two hours from the first notebook cell, including setup and model download. New work stops at 6,900 seconds, reserving up to 300 seconds for export/teardown. Two additional two-hour stages are reserved only for the conditional LoCoMo cap diagnostic. This totals twelve hours of notebook allowances and at most 859 calls. GPU idle time before the first cell or after failed provider teardown must be monitored by the user; software cannot certify provider billing. Use one shared Drive ledger and one active GPU job. Do not restart failed stages in a new folder to evade the cap. All inference ends on September 23; if development is not ready by the end of September 22, abandon the follow-up. Day 4/5 contain no new inference.

The CPU notebooks can be run first without allocating a GPU. Return each CPU/development checkpoint for verification before the next scientific stage.
